# B12 — build overhead

> **Status: measured, and the measurement does not settle the budget.**
> B12 stays open. What was measured, what it means, and what would settle it are below.
>
> **Recorded:** 2026-07-30 · **WP-14**

---

## 1. Why this number matters

[ADR-0002](../adr/ADR-0002-compile-time-orchestration.md) moved orchestration to compile
time and accepted **generator complexity as permanent legacy risk** (R1). Its
*revisit-when* clause names a threshold:

> **Revisit when:** generator maintenance cost exceeds its benefit (measured as > 3
> generator defects per delivery phase, or **build overhead > 8 % sustained**).

That clause could never have fired, because nothing measured build overhead. The budget
was declared in [14-Performance §1](../14-Performance.md) — *"Build overhead vs identical
non-FlowX code, +8 %"* — and left unmeasured through P0.

---

## 2. What was measured

`CompilerBenchmarks` drives Roslyn directly rather than timing `dotnet build`, because an
MSBuild wall-clock is dominated by restore, dependency resolution and file IO, none of
which the generator touches.

The compilation is one file: four capabilities and a flow with a compensation, an emit
and a return.

```
BenchmarkDotNet v0.15.2 · Linux Ubuntu 24.04.4 LTS
Intel Xeon Processor 2.10GHz, 1 CPU, 4 logical and 4 physical cores
.NET SDK 10.0.110 · IterationCount=30 WarmupCount=10 DOTNET_TieredPGO=0
```

| Measurement | Mean | Allocated |
|---|---:|---:|
| Compile without the generator | 4.04 ms | 678 KB |
| Run the generator only | 2.86 ms | 589 KB |
| Compile with the generator, output bound | 11.17 ms | 1 509 KB |

Two runs of the same commit put "compile without the generator" at 3.26 ms and 4.04 ms —
a 24 % swing. This is the same shared container the [P0 report](P0.md#5-is-shared-hardware-good-enough-to-decide-on)
documents, and there the 29× margin absorbed it. Here there is no margin to absorb
anything, which is a second reason the ratio below is not a verdict.

---

## 3. Why this does not settle it

**Three problems, none of them fixable by running it again.**

### The arms are not comparable

The control compiles a file containing no plan and no dispatcher. The third row compiles
that file *plus the generated plan and dispatcher* — roughly twice the code. Most of the
2.8× is binding source the control does not contain.

An application written without FlowX would have hand-written that dispatcher and paid to
bind it. So the difference is not overhead; it is partly work moved, not work added.
Reporting that ratio as "build overhead" would overstate the cost, and would be the same kind
of claim this repository has spent WP-10 through WP-13 removing.

### The generator's cost cannot be isolated this way

"Run the generator only" measures **less than the control**. That is not the generator
being free. `RunGeneratorsAndUpdateCompilation` binds only what the generator
asks for, so it does part of the control's work and skips the rest. The two numbers
overlap by an unknown amount, and subtracting them means nothing.

### One file is the worst case for a ratio

The generator's cost scales with the number of **flows**; a compilation's cost scales
with the number of **files**. A one-file project maximises the generator's share of the
total. A real application with hundreds of files and a handful of flows would show a
far smaller ratio — which means this measurement is not merely imprecise, it is biased
in a known direction.

---

## 4. What would settle it

Build the reference sample twice, from clean, with an identical final compilation:

1. **With FlowX** — the analyzer reference in place, generator running.
2. **Without FlowX** — the analyzer reference removed, and the previously generated
   `.g.cs` files included as ordinary source.

Both compile the same code; only one runs the generator. The difference is the honest
answer, and it is measured at the level a developer actually waits at.

That needs a build harness rather than a benchmark class, and it needs the sample to be
buildable in both configurations — a second project or an MSBuild condition. It was not
attempted here rather than attempted badly.

---

## 5. What this run does tell us

The generator takes **~2.9 ms** for a compilation containing one flow. Whatever the
correct ratio turns out to be, the absolute cost is small enough that the 8 % threshold
is a question about the *denominator* — how much else the build is doing — rather than
about the generator being slow.

It is also a baseline. A future change that made the generator take 30 ms would show up
here as a large regression against a committed number, which is worth having even while
the ratio question is open.

## 6. Reproducing this

```bash
dotnet run -c Release --project tests/FlowX.Benchmarks -- \
  --filter '*CompilerBenchmarks*' --warmupCount 10 --iterationCount 30
```
